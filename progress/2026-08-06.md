### 把阅读器部署成网站版（AWS Lightsail）

目标：`https://mingshi.giize.com`，服务器 54.150.201.100（Ubuntu 24.04 / x86_64 / 512 MB RAM / 2 vCPU / 20 GB SSD）。

**环境准备**

- 本机原先没装 Node，也没有 Homebrew。用官方 tarball 装了 Node v22.14.0 到 `~/.local/node-22`，软链到本来就在 PATH 里的 `~/.local/bin`，没动 shell 配置、没用 sudo。
- 服务器装了 Node v22.23.2（NodeSource）、nginx 1.24、certbot 2.9、build-essential。
- 服务器原本没有 swap，可用内存只剩 200 MB 左右。加了 2 GB swapfile（写进 fstab，swappiness=20），否则 npm install 和 SQLite 查询都容易 OOM。

**新增账号系统（网站版专用，桌面版不受影响）**

三级角色，独立的 `auth.sqlite`，放在 `backend/.userdata/` 而不是 `.cache/`，这样以后重传正文库不会覆盖账号数据。

| 角色 | 阅读/检索/AI | 上传书到临时库 | 编辑版本说明 | 改时间线数据 | 管账号 |
|------|------|------|------|------|------|
| 访客 visitor | ✅ | ❌ | ❌ | ❌ | ❌ |
| 管理员 manager | ✅ | ✅ | ✅ | ✅ | 仅访客账号 |
| 超级管理员 admin | ✅ | ✅ | ✅ | ✅ | 全部 + 改角色 |

- 预置账号：`licanhui`(admin)、`tanyayun`(manager)、`yinhaofeng`(manager)，初始密码 `password`，首次登录强制改密。
- 注册走「申请 → 待审批 → 管理员批准」流程，未批准不能登录。
- 密码用 Node 内置 `crypto.scryptSync` 加盐哈希，没引入 bcrypt 之类的原生依赖——服务器只有 512 MB，能少编译一个原生模块是一个。整个账号系统零新增 npm 依赖。
- 会话是 httpOnly + SameSite=Lax cookie，改密码/停用/改角色都会踢掉该用户全部旧会话。登录按 IP 限流（15 分钟 10 次）。
- 有审计日志表，admin 可在后台查。

**新增：临时书库**

管理员可以上传 EPUB / TXT 到独立的 `staging.sqlite`。这些书**不进主库 library.sqlite**、不建全文索引、不参与跨书比对和语义检索，但在前端书目里和其他史籍一起可读。slug 统一带 `tmp-` 前缀，物理上不可能和正库的 25 个 slug 撞车。

上传走裸流直接落盘（`Content-Type: application/octet-stream` + query 传元信息），不经过 body parser，也就不需要 multer——150 MB 的 EPUB 不会被读进内存。

**新增：版本说明 / README 编辑**

管理员在后台可编辑，存 DB，前端「关于」弹窗通过 `/api/site/content` 读取展示。桌面版拿不到这个接口，fetch 失败就静默保持原样，不影响打包版。

**账号系统由 `MINGSHI_REQUIRE_AUTH=1` 开关控制，只有网站版的 `.env` 设这一项。** 桌面版（Electron）用的是同一份 `server.js`，不设这个变量时行为与加账号系统之前完全一致——不弹登录、不建账号库、`/api/site/content` 返回空。已本地实测确认。

**登录页/注册页/后台管理页是服务端直出的 HTML**，没有动 `App.tsx` 那 7400 行。理由：账号系统要能独立改、独立上线，不该每次都重新构建整个前端 bundle。样式沿用了阅读器的古籍米黄配色。

**修掉的上线阻断项**

1. `server.js` 原来对**所有**响应无差别设 `Cache-Control: no-store`。本地无所谓，公网上意味着 154 MB 的字体每次刷新都重下。改成只对 `/api/*` 生效，静态资源按内容哈希给一年 immutable，`index.html` 用 `no-cache`。
2. `app.get("*")` 在 Express 5（path-to-regexp v8）下 `*` 不是合法模式。改成终结型中间件，绕开路径解析。
3. `/api/timeline-events` 的 PATCH/DELETE/POST 原本**无任何鉴权**——公网上任何人都能改时间线数据库。加了 manager 及以上的角色门。
4. `app.listen(PORT)` 原来监听全网卡，改成默认只绑 127.0.0.1，Node 端口不直接暴露在公网，只走 nginx。

**部署**

- nginx 反代 3100，开 gzip，`client_max_body_size 160m`（临时书库上传），`proxy_read_timeout 900s`（史料比对是 4 步串行 LLM 调用，后端自己给了 850 s）。
- systemd 常驻，`Restart=always`，`--max-old-space-size=256` 限制 V8 堆，加了 NoNewPrivileges / ProtectSystem / ProtectHome 等加固项。
- Let's Encrypt 证书已签发（2026-11-04 到期，certbot 自动续期已配）。
- 上传的数据：library.sqlite 884 MB + books 95 MB + split epub 85 MB + epub 解压缓存 169 MB + frontend/dist 157 MB。没传 donotpack、archive、mingshilu-pipeline、release 包、node_modules。

### 第二轮：按账号存储 + 两个前端 bug

**书签/札记/勾画/设置改为按账号存服务器**

原先全部走 localForage，是**按浏览器**存的：换台机器、清个缓存就没了，两个账号共用一个浏览器还会互相看到对方的札记。

改法是只换掉 `frontend/src/lib/storage.ts` 这一层——它对外只有 `readPersistedState` / `writePersistedState` 两个函数，App.tsx 里 40 多处调用一行没动。新增 `user_state` 表（`(user_id, key)` 主键，值是 JSON），存在 auth.sqlite 里，随账号删除级联清理。

- 启动时探测 `/api/user/state`：拿得到就走服务器，拿不到就退回本地（桌面版正是这条路，行为不变）。
- 写入先落本地 IndexedDB，再按 700 ms 防抖批量推服务器；标签页隐藏/关闭时强制 flush。
- 服务器确认后才把键移出脏集合，失败下次写入时重试，不会假装保存成功。
- **本地缓存按 user id 分库**（`reader_state_u<id>`），共用浏览器时缓存层也隔离。
- 单账号配额 24 MB，超了会明确回报 `skipped`，前端弹提示而不是静默丢弃。

实测：user 和 tanyayun 各写各的，重新登录后各自读回自己的，互不可见。

**新建 `user` 账号**（访客，密码 password，不预置任何配置），用于验收对照。

**修 bug 1：选段工具栏被截断**

装了 puppeteer-core 驱动真实 Chrome 实地复现。工具栏其实一直有弹出，但 `left: -99.89px`——它宽 576 px 且带 `translateX(-50%)`，选段靠近左边缘时左半边（含 ✕ 和「標記」）直接跑到屏幕外，看起来就像"没出现"。代码里从来没做过视口边界钳制。加了 `clampSelectionToolbarX()`，EPUB 和 DB-reader 两条选中路径共用。修复后实测 `left: 12, right: 588, fullyVisible: true`，10 个按钮全可见。

顺带确认一件事：选中高亮是浏览器默认蓝色，因为 `App.css` 里**从来就没有 `::selection` 规则**——桌面版也一样，不是网站版引入的回归。

**修 bug 2：大明律字号混乱**

这本 EPUB 在约 2000 个 span 上写死了内联 `font-size`（16px 810 处、19px 435 处、22px 31 处、14px 34 处）和 `color:rgb(0,0,0)`。内联样式压过样式表，阅读器注入的 `html, body { font-size: 20px }` 完全失效——正文被钉在 16px，而没有内联字号的注释继承了 20px，**注释反而比正文大**。字号调节对这本书也基本无效。

注入的 `LAYOUT_OVERRIDE_CSS` 里 `font-family` 早就用 `!important` 覆盖了，**唯独漏了 `font-size`**。补上中和规则并按语义标签重建层级，同时把纯黑内联色交还主题（否则夜间主题下这本书是黑字黑底）。这是通用规则，任何有同样毛病的 EPUB 一并解决。

期间自己写出一个叠乘 bug：标题规则误用后代选择器 `body h1 [style*=...]`，标题内的 span 又乘一次 1.5em，`20 × 1.5 × 1.5 = 45px`。改成选中标题自身（无空格），后代交给通用 `inherit`。修复后实测：16px→20px、17px→20px、22px→30px，层级正确无叠乘。

### 第三轮：Safari、性能、手机端、字体

**Safari 选不中字**（用 Playwright WebKit 复现，不是猜的）

控制台报 `Blocked script execution in 'about:srcdoc' because the document's frame is sandboxed and the 'allow-scripts' permission is not set`。epub.js 把每章渲染进带 `sandbox` 的 srcdoc iframe，没有 `allow-scripts`；Chromium 宽容，WebKit 严格执行，于是 epub.js 注入 iframe 的监听脚本被拦，选区根本建不起来。加 `allowScriptedContent: true`。WebKit 上复验：`rangeCount: 1`、工具栏弹出、9 个按钮齐全。

（中途两次误判"没修好"——探针选在了全是链接的篇目索引页上，那页本来就选不中。）

**性能：打开和切书特别卡**

抓了完整网络瀑布，三个原因：

1. **EPUB 每次都重下**。我第一轮把 `no-store` 一刀切给了所有 `/api/*`，但 EPUB 是不可变的书文件（明史 4.9 MB、国榷 23.5 MB），刷新和切书都在全量重下。改成 `private, max-age=86400, must-revalidate` + `sendFile` 走 ETag，命中就 304。
   - 踩坑：split EPUB 放在 `backend/.cache/` 下，而 Express `sendFile` 默认 `dotfiles:"ignore"`，**路径里任何点开头的目录段都会 404**。要显式 `dotfiles:"allow"`。
2. **所有静态资源都经 Node 反代**，且 `proxy_buffering off`，吞吐被压到约 300 KB/s；`gzip_static` 对反代响应无效，我预压缩的字体白压了。改成 nginx 用 `root` 直接发盘，用 `auth_request` 打到 `/api/auth/verify` 保留登录门禁。
3. 开了 HTTP/2（nginx 1.24 要用 `listen 443 ssl http2`，`http2 on;` 是 1.25.1+ 的写法）。

实测：**重复打开从全量重下变成 0.9 秒 / 0.12 MB**；冷启动到正文可读 12.3 秒。

顺带量了带宽：4 路并行每路 790 KB/s（总 3.15 MB/s），单路只有 537 KB/s，服务器自身下行 93 MB/s——所以不是服务器带宽上限，是**单条 TCP 到东京的限制**。这意味着单个大文件（字体）没法靠并行提速，只能把文件本身变小。

**字体**

- TTF → WOFF2（无损重封装，字形数据不变）：全套 154.4 MB → 78.2 MB，但对单个字体只比 gzip 再省 13–38%，**单靠它解决不了**。
- 所以同时把界面默认字体从正楷（汇文正楷）换成同为楷書的方正永樂大典：**9.82 MB → 2.89 MB，3.4 倍**。
- `fonts.css` 和注入 iframe 的声明都改成 woff2 优先、TTF 兜底，桌面版不受影响。
- 注意：已经存过 `ui-font-family` 的账号不会自动换（那是用户的选择），要在设置里手动切。

**手机端**

- 侧边栏目录滑不动：窄屏把 `.app-shell` 改成 `height:auto` 后，`.sidebar` 的 `minmax(0,1fr)` 行塌缩，`.panel-scroll` 的 `height:100%` 算不出高度，而祖先的 `overflow:hidden` 还在裁剪。给滚动容器 `max-height: 65vh` 并放开祖先裁剪。
- 更根本的一个：**响应式堆叠从来没生效过**。媒体查询里只写了 `.app-shell`（特异度 0,1,0），而折叠态是 `.app-shell.sidebar-collapsed.assistant-collapsed`（0,3,0）——偏偏两栏默认就是折叠的。三栏一直挤在 390px 里。把三个折叠变体一起列出来才修好。

**部署脚本** `scripts/deploy-web.sh`

`rsync -a` 会把 macOS 的 700/600 权限带到服务器，导致 `frontend/dist` 变成 `drwx------`，nginx 的 www-data 进不去，**全站静态资源 404**。这个坑踩了两次，所以把「传完必修权限」写进脚本而不是靠记忆。

### 第四轮：冷启动

**字体 key 迁移把当前 key 劫持了（既有 bug）**

`fontKeyMigration` 里有 `kaiti: "xiawu"`，那是 v1.0 之前"楷书=霞鹜文楷"的老映射。但 `kaiti` 现在是**合法的当前 key**（楷體·方正永樂大典），而 `migrate()` 先查迁移表再查合法表——**任何人在设置里选了方正永樂大典，下次打开都会被悄悄换成霞鹜文楷**，而且后者体积是前者的两倍。改成先认合法 key，迁移表只兜底不认识的老 key。

（排查时被自己坑了一次：探针在修复前跑过一轮，把迁移后的 `xiawu` 持久化回了服务器，于是修复后测出来还是错的。）

**内置字体互为 fallback**

楷書系三个内置字体（正楷 / 方正永樂大典 / 霞鹜文楷）在字体栈里互相当 fallback，浏览器会把它们挨个下下来——冷启动实测下载了 14 MB + 7.6 MB 两个字体，而只需要一个。宋體系那几个只用系统字体兜底，就没这问题。改成每个内置字体只留自己 + 系统字体兜底。

这两条修完，冷启动 28.38 MB → 9.99 MB（顶层口径），到正文可读 12.3 s → 9.8 s。

**登录页预取（用户提的思路，效果最好的一条）**

关键观察：阅读器需要登录，所以「浏览器没有缓存」和「用户还没登录」几乎总是同时成立。用户在登录页输密码的那几秒完全是空等，正好拿来预取 JS 包和默认字体。

在登录页注入 `<link rel="prefetch">`，资源 URL 从构建产物 `index.html` 里实时读，不硬编码，重建后不会指向不存在的文件。

实测（全新冷缓存，同一账号）：

| 登录页停留 | 登录后到正文可读 |
|---|---|
| 0.2 s | 24.8 s |
| 8 s | 14.1 s |
| 15 s | **2.6 s** |

三次都命中 5.10 MB 缓存（JS 包 + 界面字体）。剩下的 4.88 MB 是书的 EPUB，属登录后内容且因人而异，没法预取。

代价：`/assets/` 和 `/fonts/` 必须在未登录时可取，否则预取拿到 401。已改成只放行这两类，**古籍正文、检索、全部 /api 接口仍然需要登录**（已验证：未登录取 EPUB 401、取书目 401、访问首页 302）。

### 第五轮：手机端改成抽屉式布局

用户报了两个手机端问题，查下来是**同一个根因的两面**：窄屏是三栏竖向堆叠。

1. **正文飘到屏幕外**——展开左栏后，目录列表有一万多像素高，把正文整个顶下去。实测阅读工具栏落在 y=826，而视口只有 844 高，正好看不见。
2. **按键重合**——左栏自己的「‹ 收起」在品牌卡右上角，右栏那个 `position: fixed` 的展开键固定在 `top:1.2rem / right:0.8rem`，两者叠在同一位置，谁都点不准。

改成 **≤1100px 时侧栏浮层抽屉**：

- `.app-shell` 用 `100dvh`（`dvh` 而非 `vh`，手机地址栏收放时不会裁掉底部），单列，正文独占视口
- `.sidebar` / `.assistant-panel` 改 `position: fixed` 全高抽屉，左右各一，`z-index: 40` 浮在正文上，自身滚动
- 折叠态从「`width:0` + `opacity:0`」改成 `display:none`——抽屉化后前者会在屏幕边缘留一道阴影，而且仍可能吃到点击
- 抽屉打开时用 `.app-shell:not(.sidebar-collapsed) .assistant-toggle-btn { display:none }` 藏掉对侧那个固定按钮

实测三种状态（初始 / 开左栏 / 开右栏）：控件重叠全部为「无」，阅读区始终在视口内（y=218，高 552–588），页面无纵向溢出。

顺带说明：这是纯 CSS 媒体查询，同一份 bundle 同一个 URL，桌面版（>1100px 三栏并排）和 Electron 打包版都不受影响。

## 问题与思考

- **AI Key 不放服务器**。`/api/settings/defaults` 会把 `ai.apiKey` 和 `modelProviders[].apiKey` 明文返回给**任何**访问者——本地单机用没问题，挂公网上等于把火山/百炼的 key 送给所有人。所以服务器 `.env` 的 `AI_API_KEY` 留空，访客在设置面板填自己的 key。代价是访客不填 key 就只能读书和本地检索，用不了 AI 功能。
- **语义检索在服务器上不可用**。`sqlite-vec` 只有 `darwin-arm64/vec0.dylib` 和 `win-x64/vec0.dll`，没有 Linux 的 `.so`；而且 Python fastembed 在 512 MB 内存上本来也跑不动。代码里原有的自动回落逻辑会让它退到 FTS5 模糊检索。省下了 224 MB 向量库 + 259 MB Python runtime + 91 MB 模型缓存的传输和内存。要恢复的话，需要为 linux-x64 编译 vec0.so，且大概率得升配。
- **443 端口卡在 AWS 那一层**。Lightsail 的防火墙是账户级的，服务器内部改不了 ufw 也没用。certbot 加了 80→443 的 301 跳转，在 443 开放之前站点外网不可达。
- **512 MB 内存跑 884 MB 的库**是这次部署最大的隐患。FTS5 trigram 全文检索会大量走磁盘，搜索响应会明显比本地慢。目前靠 2 GB swap 兜底，如果实际使用中卡顿明显，升到 1 GB 档是最直接的解法。
- 期间踩了两个小坑：URL query 里塞未编码的中文会被 Node 的 HTTP 解析器直接 400；macOS 自带的 rsync 是 2.6.9，不认 `--info=progress2`。
- 修了一处自己写出来的 bug：鉴权中间件用 `req.path` 判断是否返回 JSON，但在 `app.use("/api/admin", ...)` 这种挂载路由里 `req.path` 已被剥掉挂载前缀，导致 API 的 403 返回了 HTML。改用 `req.originalUrl`。
- 临时书库的章数统计原先记的是解析出的章数（134），但其中 31 章的内容全被「段落至少 8 字」的规则过滤空了，实际可读只有 103 章。改成只统计真正有正文的章。
