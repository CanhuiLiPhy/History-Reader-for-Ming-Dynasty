### 二、密钥安全审计（下午）

用户提出「API key 可重设但不可查看」，审计后发现**已经在发生的泄露**。

**查到的实锤**

指纹比对（只比 sha256 前 12 位，不读取值）确认：服务器 `MINGSHI_SEED_AI_KEY` 与本地 `AI_API_KEY`（百炼 DashScope）同为 `6d22c812629b`，且这把 key 存在三个账号的 `user_state` 里 —— licanhui(admin)、tanyayun(manager)、**yijiangnan(visitor)**。

链路：`seedUserAiSettings()` 把明文 key 写进 user_state，而 `GET /api/user/state` 把整份 state map 原样回给该账号。于是「把配好 key 的账号发给别人」= 把 key 发给别人。访客打开 devtools 就能读到。

**排除掉的**：GitHub 仓库虽然公开，但全部 11 个提交的历史里搜不到任何已知 key 前缀；CLAUDE.md（含明文 key）未被 git 跟踪；`.env.example` 的 AI_API_KEY 为空；MiniMax key 未进项目目录也未进 git。

**改造**

新凭证模型：密钥只在服务端流动，客户端传来的凭证一律丢弃（因为客户端本来就拿不到）。优先级 = 账号自己的 key > 内置 key（仅 manager/admin）。访客无 key 则无 AI。

- `getPublicDefaults()` 抹除全部密钥，只留 `apiKeyConfigured` 布尔；内置 provider 仅对 manager+ 下发
- `GET /api/user/state` 读取时 `redactStateCredentials()` 抹除
- `putUserState()` 里做 write-only 合并：客户端留空 = 保留旧值，填新值才覆盖。**放在存储层而不是路由层**，任何写入路径都自动受保护 —— 否则「改个语音就保存」会把空串写覆盖真 key
- `seedUserAiSettings()` **整个移除**
- `resolveAiSettings` 加 `allowServerDefaults:false`。这条是关键：原来的 `overrides.apiKey || DEFAULT_AI_SETTINGS.apiKey` 会让访客也拿到内置 key，把角色门禁整个绕过
- 错误处理器出口加 `scrubSecrets()`：自建端点的错误格式不受控，401 时可能回显 key
- 前端列表不再显示 key 首尾字符（那本身就是泄露），改为「已配置 / 系统内置 / 未填」；内置条目无任何编辑入口

桌面版（`AUTH_ENABLED` 未设）行为逐字节不变，仍走客户端自带凭证。

### 三、MiniMax 接入

### 四、SSH 隧道（解决明文 HTTP）

端点 `http://180.184.249.155:32889/v1` 无 TLS（32889 和 443 都验过），直连意味着东京每次 AI 调用都把 Bearer token 明文发过公网。

```
AWS(东京) --SSH加密--> login-gpu --2ms机房内部--> 模型服务
```

- 在 AWS 上**新生成**专用 ed25519 密钥，用户私钥全程不离开本机
- login-gpu 的 authorized_keys 里该公钥被锁成 `restrict,port-forwarding,permitopen="180.184.249.155:32889",command="/bin/false"`
- **实测三项限制**：拿 shell 失败、转发到 22 端口被拒（000）、转发到 32889 成功（401）
- systemd 常驻，不装 autossh（512 MB 内存，零新增依赖）。**演练过断线自愈**：`systemctl kill -s KILL` 后 14 秒内自动恢复

### 六、字体覆盖率实测与调整

写了 `scripts/font-coverage.py`（纯 Python 手解 sfnt `cmap`，format 4/12，不依赖 fontTools）和 `scripts/font-report.py`（附字体真名、体积、档次判定）。

**测出的核心事实**：8 个内置字体分两档。匯文系 / 京華老宋 / 霞鶩文楷是 GBK～扩展B 档（18,000–21,000 汉字），对《明史》全书 6,728 个唯一字（繁体）缺字 0–120；三个方正字体只有 GB2312 档（~9,600 汉字），缺 1,104–1,309 字。

按频次加权更直观：方正永樂大典在《本纪第二》里 fallback 率 **1.72%**，约每 57 字一次——而它当时正是界面默认字体。

用户另给了四个字体（字酷堂竹堂楷简、方正灵飞经小楷简、方正汉文正楷简、方正文征明小楷简），实测全是**纯简体**（6,878–7,374 汉字），繁体正文 fallback 率 **44–45%**，比现有的还差一个数量级，已确认不采用。

**改动**：

- fallback 链按「谁真的补得上」重排。原来所有字体都兜到方正永樂大典，但它自己就是 GB2312 档——实测它对礼器碑的缺字填补率 **0.0%**、对瘦金 **5.7%**，每次冷启动多下 2.8 MB 却几乎什么都没补上。改成永樂大典→汇文正楷、瘦金→汇文仿宋、礼器碑→汇文正楷，三个都是 **100%**。
- 匯文系和京華老宋自身缺字为 0，链上的内置兜底全部删除（纯流量浪费）。
- 界面默认字体 kaiti → zhengkai；正文默认 mingchao 不变。服务器 5 个账号的存储值一并更新。
- 登录页预取名单换成新的两个默认字体。

冷启动字体总量 25.0 → 30.3 MB（+5.3 MB），但全部落在登录页预取窗口内。字体缓存本来就是 `immutable` + 一年 + nginx 直发，无需改动。

**没做 `<link rel="preload">`**：它只省 CSS 解析那一个来回（100–300 ms），相对 8/22 MB 的下载可忽略，代价却是每个改过字体的用户每次白下 22 MB。

### 七、修 AI 调用失败（用户报障）

用户报网页端 AI 不正常、默认模型仍是 deepseek。

**根因**：客户端把存着的整份 AI 设置发回服务端，其中 `model` / `modelOptions` 是上一套供应商留下的。凭证换成 MiniMax 后，那些名字被原样拿去打 MiniMax 端点：

```
404 The model `Doubao-Seed-2.0-mini` does not exist.
（已尝试模型：deepseek-v4-pro -> glm-4.7 -> Doubao-Seed-2.0-mini）
```

**我自己的测试漏掉了它**：验收时发的是 `aiSettings:{}`，空对象走服务端默认自然成功；真实前端发的是完整旧配置。教训——**验收载荷要照抄真实客户端会发的，不能图省事发空的**。

**两处修复**：

1. `resolveRequestAiSettings` 增加模型校验。凭证既然由服务端决定，模型就必须一起校验：凡是 effective providers 服务不了的 model / modelOptions 一律丢弃，回落到服务端默认。这样任何陈旧客户端状态都不会再打穿。
2. 4 个账号存储的 `model` / `smallModel` / `modelOptions` 重置为 MiniMax（改前备份 `auth.sqlite.bak-20260818-models`）。

回归验证：用之前 500 的同一载荷重打 → 200，实际模型 `MiniMaxAI/MiniMax-M2.5`。翻译 / 问答 / 自由对话三条链路均通过。
