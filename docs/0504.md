## 一、石匮书：从 wikisource 爬取版换为「ctext 净本 + 手工重写」组合版

### 背景

`shiku-shu`（张岱《石匮书》）原本走 wikisource 抓取通道，得到 218 章 / 4299 段。问题：
- wikisource 上石匮书各卷有大量 OCR 噪音（错字、跨页拼接错误、滚动缓冲污染产生的重复段落）
- 篇幅最大的卷（如卷十一世宗）OCR 重复段落占了约一半，AI 检索命中那些段时返回的内容是碎片乱贴
- 卷一~卷四（太祖、惠帝、成祖、仁宗）质量最好但仍多有错字

### 处理思路

按"哪段质量好就用哪段"的原则，分两段处理：

| 卷次范围 | 来源 | 处理方式 |
|---|---|---|
| 卷一 ~ 卷四（太祖/讓帝/成祖/仁宗） | `donotpack/database/石匮书.txt`（ctext.org 公开版） | 直接切片用作正确版，不做 OCR 拼接 |
| 卷五 ~ 卷十七（宣宗 ~ 太子） | shiku-shu OCR Pass 3 手工重写 | 见下面「OCR 处理三步法」 |

### OCR 处理三步法

源材料：`donotpack/database/shiku-shu-ocr/` 下 116 个 `pages-NNN-MMM.txt`，覆盖原书 pages 002-908，由 PaddleOCR-VL（在 Colab A100 上跑了约 2.5 小时）+ MinerU 双路 OCR 拿到。

**Pass 1（断句 + 去重）：** 每个 pages-*.txt → `merged/punctuated/pages-*.txt`，分 A/B/C 三档：
- A：精校，原样保留（pages 002-237 部分文件）
- B：轻改标点
- C：完整重断句 + 大幅去除 OCR 滚动缓冲产生的重复段落

**Pass 2（结构重组）：** `_make_v2.py`，pages 238-908 删页面分隔符，pages 238-758 应用安全的全局错字替换（卤→虜 / 戎山侯→成山侯 / 戎祖→成祖 / 戎國公→成國公）。

**Pass 3（按卷重写）：** Claude Sonnet 通读 pages 238-908 并按"卷"为单位重新组织成 13 个 `merged/by-volume/{05..17}-XXX本紀.txt` 文件：
- 删除页面分隔符
- 修复跨页接缝处的断句
- 对照 `mineru/` 修订形近错字（千→子、戎→成/去/死、閶→閣、卤→虜、兩→再、六→亦、宛→死、卽→即 等）
- 大幅剔除 OCR 滚动缓冲产生的重复段落污染

### 最终拼接

`merged/_make_v3.py` 把卷一~卷四（ctext 净本切片）+ 卷五~卷十七（by-volume/*.txt）拼成 `_shiku-shu-punctuated-v3.txt`（437 KB）。

### 入库

`merged/_make_import_txt.py` 把 v3 改写成数据库可识别的导入格式（用 `卷第N·章名` 作为简单章节标记替代 `========== ... ==========` 装饰），输出 `_shiku-shu-import.txt`（435 KB，17 卷）。

通过 `backend/scripts/import-local-text.mjs`：
```
shiku-shu | local-text | 17 章 | 565 段
```

## 二、读通鉴论：换源 + EPUB 一次性预处理

### 背景

`du-tong-jian-lun` 原 EPUB 是从 Kindle/AZW3 转出来的"套装 5 册"5.6 MB 版（尤学工等译注本），结构问题严重：
1. 5 个分册套了一层 wrapper，前 4 个 spine 段是封面 / 书名页 / 目录的图片，根本没正文内容
2. epub.js 解析后 `spine.spineByHref = {}`（spine 居然是空的，原因不明，可能是某个 OPF 兼容性问题）
3. 用户打开时 reader 区一直空白

### 解决路径

**Step 1：换源**

换为 `donotpack/database/读通鉴论 ([明] 王夫之 著舒士彦 点校).epub`（843 KB，Calibre 转出来的中华书局 1975 校点本，无译注）。这本结构干净，spine 18 段全是真正的正文，没有 wrapper。

**Step 2：发现并解决"in-page anchor"问题**

新 EPUB 的 NCX 有 122 个章节标记，但 spine 只有 18 个 .html 文件 —— Calibre 把多个章节塞进一个 .html，靠 `<p id="fileposNNN">` 锚点分隔。

epub.js 的"一个 spine 段 = 一章"的约定下，122 章塌缩成 18 章定位，造成：
- 顶部章节标题只在跨 spine 段时才更新（同一段里的多个章节都显示成第一个）
- 每章页数都显示 1/1（因为都共享同一个 spine 段的 location 范围）

**Step 3：一次性预处理 EPUB（不动 epub.js / 通用代码）**

写 `donotpack/database/preprocess-dutongjianlun.mjs`：
- 解 zip 到临时目录
- 对每个含多个 `id="fileposNNN"` 锚点的 `index_split_*.html`，从锚点位置切成独立的 `*_chNNN.html` 文件
- 改写 `content.opf` manifest + spine（追加 122 个新 itemref）
- 改写 `toc.ncx` 把 `file.html#filepos18695` 形式的 src 替换为新文件名
- 改写所有 HTML 内的内部链接
- 用系统 `zip` 重新打包（mimetype 在前且不压缩，符合 EPUB 规范）

输出 `backend/books/du-tong-jian-lun.epub`（951 KB），spine 从 18 个增加到 141 个（18 + 122 个 chapter 文件 + 1 个 titlepage），每章一段，epub.js 通用逻辑直接 work，不需要给 backend / frontend 加针对这本书的特殊代码。

### 入库

`backend/scripts/import-epub-source.mjs`：
```
du-tong-jian-lun | local-epub | 89 章 | 2744 段
```
（导入脚本对 text.length < 20 的章节会跳过，所以是 89 章而非 122 章；EPUB reader 端仍然是 122 章 spine，章节定位完整。）

## 三、保留的小幅通用改动

调试过程中发现并修了 3 个真实 bug，与具体书目无关，留在 v1.0：

1. **per-book last-location** — `last-location` localStorage key 改为 `last-location:${slug}`。原先全局共用一个 key 导致：用户在 ming-shi 翻到某 CFI 后切到别的书，那个 ming-shi CFI 仍被当成新书的初始位置，新书 reader 静默 fallback 到第一个 spine 段。

2. **rendition.resize race fix** — `ResizeObserver` 创建时立刻 fire 一次回调；如果赶在 `display()` 之前跑，epub.js 内部 `this.manager.resize()` 会因 manager 还没建好而抛 `Cannot read properties of undefined (reading 'resize')`，打断 init 流。修法：resize 前检查 `rendition.manager` 存在 + try/catch 兜底。

3. **scrollPendingAnchorIntoView 改为 iframe-only 滚动** — `element.scrollIntoView({block:"start"})` 在 iframe 里调用时浏览器为了把元素贴到视口顶端，会同时滚动 iframe 和外层 window，导致每次点目录跳转后 reader 顶部那条书目栏被顶出去。改成调用 iframe 自己的 `defaultView.scrollTo`。

## 四、回滚的尝试

调试过程中曾尝试改通用 chapter 解析逻辑（在 `buildChapterNavigationMap` 里给同 spine 段的多锚点做均匀分布、在 `deriveChapterState` 里加 multi-match-by-locationIndex、加 `refineNavWithRenderedSection` hook），均不准，且对其他书目可能引入回归。最终全部回滚，改走"预处理这本书的 EPUB 数据"的路径。

教训：通用层的猜测式修复（even distribution）在数据本身就模糊时只能近似；通过预处理把数据变干净，让通用逻辑直接 work，更可靠。
